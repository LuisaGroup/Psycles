# Host-prepared Cycles camera inverse

## Structural cause

The source reference is Cycles 5.2.1 at
`/home/mike/Projects/blender-cycles-trace-5.2`, revision
`cb168525138fecc792cc393f94afc39582b0103c`.
`scene/camera.cpp:284` computes `worldtocamera = transform_inverse(matrix)`
on the host; line 347 uploads that result into `KernelCamera`.
The Camera Data node, texture coordinates and camera-space vector transforms
read that precomputed field. These source files have no local modifications.

Psycles uploaded only the forward camera transform. The production
`PathCyclesSvmKernelGlobals`, native surface setup and native NEE setup
instead recorded `inverse(parameters.camera_transform)` in device code.
The matrix is a runtime kernel argument, not a JIT constant. Removing
duplicate expressions cannot move this computation to the host.

This was verified in the full original Lone Monk kernels, not inferred from
the C++ calls alone. In the pre-change retained-render evidence
`/var/tmp/psycles-cycles-sort-lone-monk-repeat-8kfoPI`, surface final IR
`hip_kernel_final_3.ll:1776` starts the camera cofactor calculation from
kernel-argument components, and line 1885 reduces the determinant.
NEE final IR `hip_kernel_final_4.ll:888` extracts the same runtime camera
matrix, with its determinant reduction at line 1038. Each final shader has
one surviving camera inverse: the duplicate AST calls were already merged.
The other surface matrix inversions have object/instance inputs and are
not counted as camera work.

There is also a semantic difference: a general 4x4 inverse emits Inf/NaN
for singular affine matrices, whereas Cycles' `transform_inverse_impl`
regularizes a zero determinant by perturbing the three diagonal entries,
then uses its specified fallback if the determinant remains zero.

## Change and permanent regression

`RenderKernelParameters::camera_inverse_transform` now carries the
host-prepared inverse of the existing renderer camera pose. This follows the
source camera-data lifetime and affine inverse semantics. Session initialization
uses the existing `compiler::cycles_inverse_affine_transform`; the three
device adapters load the uploaded inverse. Forward camera transforms and
object transforms are not changed. No compiler/inlining policy, SVM words,
payloads, PC control flow, feature masks or default initialization semantics
are changed.

`tests/test_luisa_cycles_camera_transform.cpp` invokes the production
KernelGlobals and NEE setup.
One compiled kernel receives eight different camera matrices as runtime
arguments, including identity, translation, rotation, nonuniform scale,
negative scale, shear, one collapsed axis and three collapsed axes.
It checks all inverse matrix components and the
orthographic NDC service against Cycles, and requires no `MATRIX_INVERSE`
operation in the adapter's XIR. Thus constant folding of test inputs cannot
hide an accidental return to device inversion.

The expected data is generated by `tools/cycles_camera_transform_oracle.hip`,
which executes the original Cycles `transform_inverse` and
`camera_world_to_ndc` on HIP. The shared fixture contains inputs only.
It introduces no CPU reference renderer or duplicate reference evaluator.

```sh
/opt/rocm/bin/hipcc --offload-arch=gfx1201 -DHIPCC -std=c++20 -O3 \
  -I include -I /home/mike/Projects/blender-cycles-trace-5.2/intern/cycles \
  tools/cycles_camera_transform_oracle.hip -o /tmp/camera-transform-oracle
/tmp/camera-transform-oracle
```

The old implementation failed the initial regression with two device
inverse operations and all 24 output lanes in each singular case disagreeing
with Cycles' finite results (`hip-red-fixture.log`). The final standalone
regression drops duplicate Camera Data handler calls to avoid depending on
the separately pending Stack storage API change. It retains all 16 inverse
components and the three NDC coordinates; existing dedicated Camera Data
node tests remain in the focused suite. An earlier test-fixture
attempt omitted bindings for the inactive non-background resources and
crashed during host dispatch; that fixture error was corrected before the
semantic red run and is not a Luisa compiler bug.

Build and regression evidence resides at
`/var/tmp/psycles-camera-precompute-tHuozf`.

## Full original scene and measured impact

All runs use Lone Monk frame 4, RX 9070 XT HIP, 1440x1080, 256 spp, seed 0,
adaptive sampling/denoising off, native SVM and the existing staged wavefront
shader-locality sort. No builds, other GPU tests or image comparisons ran
during the timed integration intervals. The fresh control already contains
the added, unused uniform field, isolating the inverse-consumption change
from the uniform ABI extension.

| Configuration | `render_samples` | Surface GPU | NEE GPU |
|---|---:|---:|---:|
| Device inverse, fresh control | 16.0996 s | 8.136462 s | 0.782041 s |
| Host inverse | 16.0200 s | 8.133504 s | 0.729423 s |
| Host inverse, repeat | 16.0446 s | 8.135749 s | 0.743303 s |

NEE improves about 5.0--6.7%, while the complete rendering interval improves
only about 0.34--0.49%. Surface is effectively unchanged. This is not the
main remaining performance difference from Cycles.
Both retained runs have identical final surface and NEE LLVM IR. Compared
with the same-ABI control, surface final IR loses the camera determinant
calculation (two object inversions remain), and NEE has no matrix inverse.
The raw final IR files have 146 / 132 fewer lines respectively; this is a
small local reduction, not another large whole-renderer IR collapse.

Surface remains 1271 launches, 256 VGPRs, 3424 B scratch, block size 512.
NEE remains 1199 launches, 256 VGPRs, 1472 B scratch, block size 32. Surface
thread totals are 819493376 / 819493376 / 819492352, and NEE totals are
429715616 / 429715264 / 429716160; the negligible rounded-dispatch variation
does not explain the measured NEE improvement.
The added 64 B are dispatch-uniform parameters, not per-path storage.
The coroutine frame is unchanged: 88 fields, 416 B payload + 28 B scheduler
state = 444 B SoA (448 B AoS).

The two retained images have Combined relative RMSE 0.01111908 / 0.01113658
against the established Cycles HIP image, with zero non-finite pixels in
all eight compared passes. DiffInd (~0.141) and GlossInd (~0.162) remain
unresolved. The direct first-retained/control comparison has Combined
relative RMSE 0.00046575, also with zero non-finite pixels; bit-identical
images are not claimed.

## Separate camera-coordinate integration gap

This patch does not establish full camera ABI equivalence. A follow-up audit
found that `export_psycles_scene.py::_camera_transform_without_scale` exports
the normalized Blender camera pose without the basis conversion performed
by Cycles' `blender/camera.cpp::blender_camera_matrix`. For perspective and
orthographic cameras Cycles reflects the local Z axis; panorama has its own
basis conversion. The renderer's ray generation uses local negative Z, while
the copied SVM handlers expect the converted Cycles camera matrices.

The existing Vector Transform oracle regression supplies already-converted
matrices directly. The new regression likewise tests inverse preparation and
production adapter consumption of explicit matrix inputs, not the complete
Blender-camera import boundary. A real imported-scene Camera Data / Camera
texture-coordinate / Vector Transform oracle is required for that separate
binding correction. It must not be treated as solved by these passing tests
or by the small inverse-precomputation performance gain.

The real `camera_data` probe was then generated with the existing
`tools/create_cycles_shader_probe.py`, rendered by Cycles HIP at 64x64 / 16
spp and exported unchanged. Evidence is at
`/var/tmp/psycles-camera-basis-audit-ALcdKA` (`create.log`, `cycles.log`,
`cycles.exr`, `cycles.json`, `export/scene.json`, `psycles.log`). The full
native-SVM Psycles renderer currently fails even earlier, in front-end
lowering: Camera Data outputs are reported as not lowered. No Psycles EXR
was produced, so no measured camera-coordinate image differential is
claimed. This import/lowering gate must be fixed before validating the
separate basis-conversion correction against that real-scene oracle.
